52. BUILD ORDER AND MILESTONES
============================================================

52.1 Rules of sequencing

1. Milestones are strictly ordered M0 -> M10. **Do not start a milestone until the previous one is green.** "Green" means: its `make` proof target exits 0 on a clean clone, in CI, twice in a row, with no manual step.
2. Every milestone ends with a single command, `make mN-verify`, that prints a machine-parsable block and exits non-zero on any failure. No milestone is "done by inspection".
3. Every milestone adds a row to `docs/STATUS.md` generated by `make status` from the actual CI artifacts. Never hand-edit that file.
4. A thin vertical slice (generate -> ingest -> reconstruct -> replay -> visible in UI) must exist at **M3**. Nothing after M3 may break the slice; `make demo-slice` runs in every subsequent milestone's verify target.
5. The polyglot long tail (section 19) begins only at **M9**. Do not scatter languages across M0-M8 to look productive. Languages added before M9 are only those the core genuinely needs: Python, Rust, Go, TypeScript, SQL, Bash, Dockerfile, YAML, TOML, Makefile, plus Haskell at M6 (differential oracle) and C at M4 if and only if the liveness hot loop demonstrably needs it with a benchmark to prove it.
6. If a milestone cannot be completed as specified, stop and report per section 56. Do not silently redefine the acceptance criteria.

52.3 M0 — Skeleton and toolchain

- Goal: a clone of the repo builds, lints and tests an empty system, offline, on Linux/macOS/WSL2.
- Deliverables: directory tree per section 8; `docker-compose.yml` (postgres, redis, api, web, worker) with pinned digests; `Makefile` with the full target vocabulary; `.tool-versions`/`rust-toolchain.toml`/`go.mod`/`package.json` with exact pins; `.github/workflows/ci.yml`; `.editorconfig`; pre-commit hooks; `make bootstrap` that installs nothing outside the repo and container images.
- Acceptance: `docker compose up -d` reaches healthy for all services in < 90s; `make lint test build` exits 0 with zero test cases skipped; CI runs with `--network=none` for the test job and passes; `git clean -xdf && make bootstrap && make m0-verify` passes on a second machine profile in CI matrix.
- Proof: `make m0-verify` prints versions of every toolchain, the compose health table, and `M0 OK`.
- Demo capability: none. This milestone unlocks nothing user-visible and must not be presented as progress on the product.

52.4 M1 — Generator and ground truth

- Goal: seeded synthetic telemetry with recorded ground truth, honestly generated.
- Deliverables: `spectra-gen` CLI; scenario definitions in `scenarios/*.toml`; at least 6 scenarios covering identity, session, credential, privilege, process, network, service-account and trust dimensions; ground-truth file `truth.json` recording the true attack step sequence and true control dependencies; manifest with BLAKE3 hash and seed; per-source sequence chaining (used later by liveness).
- Acceptance: identical seed produces byte-identical `bundle.jsonl` and identical manifest hash across 3 runs and across Linux/macOS; `truth.json` is never read by any ingest, reconstruction or kernel code — enforced by a build-time import/dependency test and a grep gate in CI; generator emits volume/timing statistics that are computed, not declared.
- Proof: `make m1-verify` (hash triple-run equality, truth-isolation gate, scenario schema validation).
- Demo capability: `spectra gen --scenario s1 --seed 7` produces a dataset you can show on screen. Nothing more.

52.5 M2 — Ingest, entity resolution, event store

- Goal: heterogeneous records become entity-resolved, time-indexed, stable-ID events in Postgres.
- Deliverables: parsers per source type; normalization to the canonical event schema (section 12); entity resolution with deterministic tie-breaking; `EventId` assignment stable across re-ingest; SQL DDL and migrations; `spectra ingest`.
- Acceptance: re-ingesting the same bundle yields the identical `EventId` set (`SELECT count(*) FROM events WHERE event_id NOT IN (...)` = 0); ER precision/recall measured against `truth.json` **only in the evaluation harness**, reported as numbers from a real run; ingest of a 2M-record bundle completes within the documented budget and the measured number is written to `bench/ingest.json`; no `NOW()`, no random UUIDs, no wall-clock in any ID derivation (lint rule `no-nondeterminism` passes).
- Proof: `make m2-verify`.
- Demo capability: query the event store, show entity clusters. Still no product story.

52.6 M3 — VERTICAL SLICE (mandatory earliest end-to-end)

- Goal: one command takes a scenario from generation to a replayed control configuration rendered in the browser.
- Deliverables: (a) deterministic reconstruction producing the state-transition timeline and the causal graph; (b) `rules.toml` v1 with at least 25 rules compiled to Rust; (c) the concrete control simulator driven by the **same guard AST** as the future kernel (section on CCL); (d) `POST /api/replay` accepting a control configuration and returning the deterministic outcome; (e) React view: timeline, causal graph, control toggle panel, outcome banner.
- Acceptance:
  - `make demo-slice` runs headless end to end in < 3 minutes and asserts on real output, not on exit codes alone.
  - Toggling `session_binding` from 0 to 1 in the API changes the terminal node of the attack path, and the changed node is asserted by test, not screenshotted.
  - Two identical replay requests return byte-identical JSON including ordering of arrays.
  - The UI renders the same terminal node as the API returns (Playwright test compares DOM text to API JSON).
  - Removing the LLM service from compose changes nothing: `make demo-slice NO_LLM=1` passes with identical outputs except narration fields, which must be absent, not empty-stringed.
- Proof: `make demo-slice` plus `make m3-verify` (which runs demo-slice + determinism + no-LLM run).
- Demo capability: **the product exists.** You can show: here is the attack, here is the state reconstruction, flip this control, the chain dies at step 4. Every claim on screen traces to real computation.

52.7 M4 — Liveness, licenses, silent envelope, fixpoint

- Goal: ECLIPSE pipeline stages A-D.
- Deliverables: per-source liveness with BLAKE3 chain checks and q99 inter-arrival from this run's own data; `liveness.json`; Bellman-Ford difference-constraint pass voiding backdated licenses; semi-naive grounding with provenance producing the AND/OR hypergraph; silent instance generation gated on `∀s ∈ producing_sources(τ): ¬live(s,I)`; the ~40 obligation axioms, each with a must-fire and a must-not-fire unit test; `P_min` and `P_max`; Dowling-Gallier fixpoint under a cut mask.
- Acceptance: all 40 obligation axioms have both tests and both pass; grounding sizes are measured and written to `bench/grounding.json` with caps recorded; a rule-ordering property test (≥ 500 randomized orderings) yields byte-identical fixpoints; `Reach(P_min) ⊆ Reach(P_max)` asserted on every fixture; the delete-effect linter rejects a deliberately malformed rule in a negative test; ghost (silent) instances never appear in any observed-event count — asserted by a test that counts both.
- Proof: `make m4-verify`.
- Demo capability: show blind windows per source on the timeline and the GHOST-rendered hypothetical steps, clearly marked as permissions, not observations.

52.8 M5 — Two-sided minimal cut and certificate

- Goal: ECLIPSE stages E and the certificate object.
- Deliverables: Reiter/MARCO hitting-set loop over clause DB Ψ; minimum-cardinality model by popcount-ordered branch and bound over `u64` masks; threshold-literal implications `x_{k,ℓ+1} → x_{k,ℓ}` enforced; witness-tree extraction; `S_opt` on `P_min`, `S_rob` on `P_max`; corridor sets `Ψ_min`, `Ψ_max`; blindness premium `S_rob \ S_opt` with the responsible licenses named; certificate serialization exactly as specified in section on ECLIPSE, content-addressed by BLAKE3; downgrade to subset-minimal with the `subset_minimal_only` flag when `|A| > 64`.
- Acceptance: on every fixture, an exhaustive brute-force over all cuts (fixtures sized so this is feasible, `|A| ≤ 18`) confirms `|S_opt|` and `|S_rob|` are truly minimum; the antitonicity test over the control lattice passes (raising any level never re-enables the goal); a flagged run (capped grounding, greedy cover, or subset-minimal) can never carry `mode: ROBUST` — negative test asserts the builder refuses; blindness premium is non-empty on at least two fixtures and each element names ≥ 1 license.
- Proof: `make m5-verify`.
- Demo capability: PROVE returns a real certificate hash and a real minimum cut.

52.9 M6 — Independent Go checker and differential gates

- Goal: the certificate is verifiable by code that shares nothing with the solver.
- Deliverables: `spectra verify` as a separate Go module under `checker/` with its own `go.mod`, no dependency edge to the Rust workspace (enforced by a CI dependency-graph test); it re-grounds from hashed inputs and checks (a)-(f) per the ECLIPSE spec; a Haskell reference admissibility checker for license logic used as a differential oracle; the concrete-simulator-vs-kernel agreement gate over 256 randomized control configurations per fixture; Z3 as a test-only oracle, never a runtime dependency.
- Acceptance: `spectra verify` returns OK on all valid certificates in < 50ms for a 2k-instance scenario, measured and recorded; a mutation suite of ≥ 30 corrupted certificates (flipped cut atom, forged license, tampered bundle hash, truncated Ψ, wrong invariant `U`, witness leaf that is not a real `EventId`) each produce a distinct, specific failure and a non-zero exit; Rust-kernel vs Go-checker vs Haskell-oracle disagreement on any fixture fails the build; `grep -r` proves the checker links no Rust artifact and no shared crate.
- Proof: `make m6-verify`.
- Demo capability: the terminal pane in the demo that independently validates the proof in front of the viewer.

52.10 M7 — Degradation, tampering, redundancy, observation set, frontier

- Goal: the second research axis and ECLIPSE stages F, G, H.
- Deliverables: degradation matrix from 100% to 30% completeness in 10-point steps, crossed with the six perturbation modes (deletion, delay, duplication, reordering, corruption, targeted suppression), ≥ 20 seeds per cell; redundancy index `red(i,j)` from Ψ; decisive observation set (exact ≤ 3, greedy beyond with the `ln n + 1` bound printed and the `greedy_cover` flag set); multiple-choice knapsack frontier over declared costs; results serialized to `results/*.json` and rendered by the analysis language (R or Julia) into `docs/RESULTS.md` figures.
- Acceptance: **the invariant — zero false ROBUST verdicts across the entire matrix**, checked against generator ground truth, is asserted and the count printed; every published number is regenerated by `make bench` from scratch, and `make docs-check` fails if any number in `RESULTS.md` differs from `results/*.json`; costs come only from `costs.toml` and the test suite includes a case with no `costs.toml` where the frontier is expressed in control counts and says so; no probability, confidence score or dollar figure appears anywhere in output — enforced by a lexical gate on the JSON schemas and a CI grep over rendered docs.
- Proof: `make m7-verify` (runs the matrix at reduced seed count in CI, full matrix in `make bench`).
- Demo capability: the stability strip and the "which single log source collapses the ambiguity" beat.

52.11 M8 — Full UI and PROVE flow

- Goal: the flagship interaction, complete.
- Deliverables: control panel with per-control **levels** (not booleans); PROVE button; certificate header with mode, cut, corridor count and hash; counterexample derivation tree with real `EventId` leaves, expandable to the raw event record; blindness-premium panel naming licenses and their windows; GHOST styling for silent instances with a legend; embedded checker pane streaming real `spectra verify` output; stability strip; flag badges that are impossible to hide.
- Acceptance: Playwright suite asserts every on-screen number against the API response; a test asserts that a flagged run renders the flag badge and that `ROBUST` is not rendered; colour and GHOST distinction pass a contrast check; the UI works with the LLM service absent (narration panel renders an explicit "narration unavailable" state, never fabricated text); zero client-side computation of any verdict — a test greps the bundle for forbidden solver symbols.
- Proof: `make m8-verify`.
- Demo capability: the full 10-minute demo of section 54 can be performed by hand.

52.12 M9 — Polyglot surface and performance

- Goal: the remaining languages, each with a stated technical reason, plus measured performance.
- Deliverables: per section 19, each additional language ships as a real component with a justification line in `POLYGLOT.md`, its own tests, and a place on a code path or a documented offline workflow (e.g. YARA for artifact-pattern fixtures, Verilog/VHDL for the hardware-attestation sensor model, Solidity for the append-only evidence-anchor experiment, WebAssembly for the in-browser fixpoint replayer, Assembly for the BLAKE3 chain inner loop with a benchmark against the portable version, MATLAB/R/Julia for analysis, Swift/Kotlin/ObjC/Dart for platform telemetry collectors).
- Acceptance: every language in the target list either (a) has a component, a test and a justification, or (b) is explicitly listed in `POLYGLOT.md` as not used, with the reason. **No language may exist solely as a hello-world or a re-implementation of an existing CRUD path** — a reviewer checklist item and a CI check that each language directory contains at least one test that fails when its source is mutated. Performance numbers for the Assembly/C paths must include the portable baseline; if the optimized path is not faster, say so and keep the baseline as default.
- Proof: `make m9-verify` + `make polyglot-report`.
- Demo capability: a credible repository language surface backed by real code.

52.13 M10 — Documentation, demo, release

- Goal: the repository is presentable and the demo cannot rot.
- Deliverables: every document in section 53; the recorded assets of section 54; the GitHub surface of section 55; `v0.1.0` tag and release notes; `make demo` non-interactive; `make release-check` running the union of all `mN-verify` targets plus docs checks.
- Acceptance: `make release-check` green from a clean clone with no network beyond image pulls; every README claim maps to a passing test or a command in the demo transcript; `docs-check` confirms no number in docs is unbacked; `LIMITATIONS.md` contains every item from the ECLIPSE "may never claim" list verbatim in substance.
- Proof: `make release-check`.
- Demo capability: a stranger can clone and reproduce the demo in 10 minutes.

56.2 Absolute prohibitions

- Do not write a test that asserts only `exit 0`, `is not None`, or `len(x) > 0` on a demo-path behaviour.
- Do not mark a test skipped to make a milestone green. Do not lower a threshold to make a gate pass. Do not delete a failing fixture.
- Do not commit a number to any document that you did not obtain by running code in that commit.
- Do not implement a stub that returns a plausible value. If a function is not implemented, it raises/panics and its caller is not on the demo path.
- Do not use an LLM anywhere in the reconstruction, liveness, grounding, cut, certificate or checker paths.
- Do not add a language by translating existing logic. Do not add a language directory without a test that fails under mutation.
- Do not claim ROBUST, minimality, soundness or prevention beyond the wording permitted in the ECLIPSE "may never claim" list.

56.3 Reporting protocol to the human

After every milestone, and whenever asked for status, report in exactly this shape:

```
MILESTONE M<n> — <GREEN | RED | PARTIAL>

WHAT RUNS
  <command>  ->  <one-line real output, copied, not paraphrased>
  ...

EVIDENCE
  anti-slop: 24/24 PASS        (or: 22/24, failing rows listed below)
  determinism: 3/3 identical   bundle blake3:<hash>

  measured: grounding 2,104 instances; checker 11ms; ingest 418,220 events in 42s

WHAT I DID NOT BUILD
  <explicit list; never silently omitted>

WHAT IS STUBBED OR FAKED
  <file:line — what it returns — whether it is on the demo path>
  (If this list is non-empty and any entry is on the demo path, the milestone is RED.)

FLAGS ON THIS RUN
  grounding_capped | subset_minimal_only | greedy_cover | none

NEXT
  <the single next milestone and its first task>
```

Rules for reporting:

1. Show commands and their real output. Never describe output you did not produce.
2. Never say "should work", "is production ready", "fully verified", "proves the system is secure", or "detects attacks". Say what ran, on what data, with what result.
3. If you stubbed, mocked, hardcoded, shortened a loop, reduced a seed count, or skipped a gate to get something to run — say so in `WHAT IS STUBBED OR FAKED` in the same message, unprompted, with file and line.
4. If a gate fails and you cannot fix it, report RED with the failing assertion text and your diagnosis. Do not proceed to the next milestone.
5. Distinguish measured from expected. A number without a command that produced it must not appear.
6. When a design decision was forced, write the ADR before reporting.
