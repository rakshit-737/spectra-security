# C - record framing and field scanner on the ingest hot path
Tier: B
Status: not started
Owning spec section: 73 (Part II), which supersedes Part I section 31.7
Milestone: M9 - Polyglot surface and performance

## The promise

This directory will hold a second implementation of record framing and field scanning, written in
C, driven over the same input bytes as the Rust ingest path, and timed against it. The promise is
the comparison itself, not its outcome. Part II section 73.1 states the Tier B honesty requirement
in exactly those terms: the C component is justified by the existence of the benchmark, not by its
result. If the Rust scanner turns out to be faster, `docs/bench/ingest.md` says so, this directory
stays as the comparison arm, and no document anywhere claims a speedup. The sentence "we rewrote
the hot path in C for speed" is forbidden by Part II section 73.1 and must not appear in this
repository or in any commit message.

Nothing has been measured. Nothing has been built. There is no number here and there will be none
until `make bench` has run on declared hardware and written its result with a run manifest hash,
per Part II section 73.11.

The second, quieter half of the promise is differential rather than performance: the frame
boundaries and field boundaries this scanner computes must agree with the Rust path on the same
input. Two independently written scanners that agree make a framing bug visible; one scanner makes
it silent.

Explicitly not promised: correctness of ingest semantics, which belongs to the Rust path and to the
byte-conservation law of Part II section 59; any statement about production throughput; and any
claim that C is the faster language for this job.

## Consumer edge

The declared consumer is `tests/differential/scanner_rust_vs_c.rs`, owned by the Rust kernel
component and not by this one - Part II section 73.3.1 forbids self-consumption, and a component
whose only consumer is its own test suite fails the audit with `SELF_CONSUMING`.

If this directory is deleted, ingest keeps working. The Rust path is the product path and it does
not call this scanner. What breaks is precise and limited: the differential test loses its second
arm and cannot resolve, and the scanner comparison section of `docs/bench/ingest.md` loses the data
it is generated from, so `make reproduce` can no longer regenerate that section. That is a gate and
a published artifact, which is what Part II section 73.3 requires a consumer edge to be. It is not
a product outage, and this file does not pretend otherwise.

## How it is exercised

- CI job: `polyglot-b / ingest-scanner-c`, the job name Part II section 73.4 writes verbatim in the
  manifest example for this component.
- Tier: T1 on changed paths. Part II section 73.9 gives Tier B "changed-path jobs plus all
  differential gates" per PR, and T2 nightly for the full run and the mutation leg. Part II section
  74.4's cost table places the Tier B hot-path differential in T2 because it needs the
  `spectra/toolchain-b` image, which carries clang and gcc.
- Component entrypoint: `make -C c/ingest_scanner bench` (Part II section 73.4).
- Audit that licenses this directory to exist at all: `make polyglot-audit`.
- Published comparison: regenerated by `make bench` and re-derived from a clean clone with the
  network off by `make reproduce`.

## Mutation check

Operator `truncate_output_fields`, seed 7331, both fixed by the manifest example in Part II section
73.4. The audit applies it in a scratch worktree to this component's output, not to its source: the
final field of every record the C scanner emits is dropped.

The gate that must go RED is `polyglot-b / ingest-scanner-c`, at the named assertion
`scanner_rust_vs_c::field_boundaries_agree`. Part II section 73.4 requires `expect_red` to name both
a job and a specific assertion, or the lint fails with `MUTATION_UNDERSPECIFIED`.

The reasoning is the point of the check: if the last field of every record can vanish and the
differential still passes, the differential is not comparing field boundaries and this component is
PADDING under Part II section 73.6. The only admissible responses to a PADDING verdict are to give
the component a real consumer edge or to delete the directory in the same commit. Writing a better
rationale is explicitly not one of them.

## Not yet decided

- Part I section 31.7 gave C two jobs: a lock-free shared-memory ring buffer with a stable ABI, and
  a `ptrace`-based syscall tap. Part II section 73.1 names only framing and field scanning. Whether
  the ring buffer and the tap survive anywhere is unresolved, and the tap in particular is the thing
  that captures the assembly fixtures' syscall traces (`fixtures/asm/`), so deleting it silently
  would orphan that component's capture path.
- The toolchain pin. `clang-17.0.6` and the `vendor/llvm/` path appear in Part II section 73.4 as
  manifest illustration, not as a decision. The real pin is whatever `toolchains.lock` records, and
  `toolchains.lock` does not exist yet.
- The per-PR tier. Part II section 73.9 puts Tier B differential gates in the per-PR set; Part II
  section 74.4 puts the Tier B hot-path differential in T2. Both are Part II. The likely
  reconciliation is that the changed-path job is T1 and the full timed comparison is T2, but that is
  a reading, not a ruling, and per KICKOFF section 2 it is not settled silently.
- Whether the benchmark is a timed comparison, an instruction-count comparison, or both. A
  wall-clock measurement cannot appear in any path that affects a bundle's bytes (Part II section
  59), so the benchmark lives in the nightly tier and its declared hardware has to be named before
  any figure is published.
- Whether this scanner is exercised over the full ingest corpus or a declared subset.
